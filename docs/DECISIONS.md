# 설계 결정 기록

이 문서는 여러 세션에서 반복 논의하지 않아야 할 장기 결정을 기록한다. 새 결정은 기존 항목을 덮어쓰지 말고 상태와 대체 관계를 명시한다.

## D-001 · Local-first 실행 경계

- 상태: 적용
- 결정: CLI 실행, repo 접근, 상세 프롬프트, 로그, 비밀정보는 Local Office가 소유한다.
- 이유: 코딩 에이전트 실행에는 높은 로컬 권한이 필요하며 공개 서비스와 같은 신뢰 경계에 둘 수 없다.
- 결과: 서버 기본 바인딩은 `127.0.0.1`이고 외부 공유는 별도 승인 흐름이 필요하다.

## D-002 · Office는 canonical Git repo

- 상태: D-009에 의해 대체됨
- 결정: 일반 폴더가 아니라 `git rev-parse --show-toplevel`로 확인한 repo root를 Office 경계로 사용한다.
- 이유: 작업, Git 이력, branch, worktree와 에이전트 배치를 하나의 일관된 경계로 묶기 위해서다.
- 결과: 유효한 repo가 없으면 Office 종속 기능을 활성화하지 않는다.

## D-003 · 역할과 실행 프로필 분리

- 상태: 적용
- 결정: 역할 프리셋은 역할 지식·mode·전문 태그만 가지며 adapter와 model은 사용자 에이전트가 가진다.
- 이유: 같은 역할을 Codex, Claude, OpenCode, 사내 호환 CLI에서 재사용하기 위해서다.
- 결과: 역할 변경은 CLI 연결과 개인 추가 지시를 보존한다.

## D-004 · 명시적인 프롬프트 계층

- 상태: 적용
- 결정: 숨은 프로젝트 프롬프트를 두지 않고 역할, 개인, Office, 팀, 현재 작업 순서로 조립한다.
- 이유: 어떤 지시가 실행에 영향을 주는지 UI와 로그에서 설명 가능해야 한다.
- 결과: 새 지시 범위를 추가할 때 저장 모델, UI, Runner, 문서를 함께 변경한다.

## D-005 · Office 아래 여러 독립 팀

- 상태: 적용
- 결정: Office 전역 단일 master 대신 팀마다 lead, members, instructions, routing, workflow를 둔다.
- 이유: 한 repo에서도 프론트엔드, 플랫폼, QA 등 서로 다른 책임과 운영 규칙이 필요하다.
- 결과: 팀을 선택한 미션은 해당 팀의 직원 안에서만 라우팅한다.

## D-006 · 직급 순서가 아닌 모드 라우팅

- 상태: 적용
- 결정: PM→개발→디자인→QA 같은 고정 순서를 기본값으로 강제하지 않는다.
- 이유: 작은 수정은 바로 구현할 수 있고 작업마다 필요한 전문성이 다르다.
- 결과: adaptive, manual, sequential 세 모드를 제공하며 명시적 sequential만 고정 순서를 사용한다.

## D-007 · repo 쓰기 충돌 방지

- 상태: 적용
- 결정: shared 경로에서는 쓰기를 직렬화하고 병렬 작업은 agent별 worktree로 격리한다.
- 이유: 여러 프로세스가 같은 파일과 index를 동시에 수정하는 충돌을 막기 위해서다.
- 결과: 동시 실행 수가 남아도 같은 shared 경로 작업은 queued가 될 수 있다.

## D-008 · Local Office와 Web Hub 분리

- 상태: 계획 유지
- 결정: 향후 Web Hub는 카탈로그·공개 리포트·마켓플레이스를 담당하고 로컬 CLI를 직접 실행하지 않는다.
- 이유: 공개 서비스와 로컬 실행 권한을 분리하기 위해서다.
- 결과: 두 표면 사이에는 검증된 manifest와 사용자 승인 데이터만 이동한다.

## D-009 · Office는 로컬 폴더, Git은 선택적 확장

- 상태: 적용
- 결정: Office의 실행 경계는 사용자가 지정한 존재하는 로컬 폴더다. Git 저장소여야 할 필요는 없다.
- 이유: 탐색·초기 구현은 Git 초기화 전에도 시작할 수 있고, 중간에 Git을 도입해도 Office·팀·작업 이력을 유지해야 한다.
- 결과: 폴더 모드에서는 팀·작업·자동화·CLI 실행을 허용하고 Git 전용 표면만 비활성화한다. 후에 Git이 탐지되면 새로고침으로 해당 표면을 활성화한다.

## 결정 추가 규칙

- 장기간 유지할 경계나 데이터 계약만 추가한다.
- 구현 세부, 일시적 버그, 단순 작업 계획은 기록하지 않는다.
- 결정을 바꾸면 기존 항목을 `대체됨`으로 표시하고 새 결정 ID를 연결한다.
